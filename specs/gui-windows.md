# General behaviour

Related: specs/gui-title-row.md, specs/gui-side-panel.md, specs/gui-main-area.md, specs/gui-preview.md, specs/gui-dialogues.md, specs/plugins.md, specs/scope.md, specs/core-types.md

**Session restore.** Closing Rick and opening it again brings back exactly what was left: every window with its position and size (*Window geometry*, below), its workspace tabs in order with the active one, each workspace's layout and every pane's path, sort, filter, column widths and scroll position, and the side panel's state. The session is saved continuously, so a crash loses nothing but the last few seconds. A pane whose location no longer exists opens at its nearest existing ancestor with a note in the footer; one whose provider is not mounted opens at Home.

**Saved layouts.** A user can arrange a window — its workspace tabs and their panes — then save that arrangement as a named layout and mark it as the start layout; Rick then opens with that layout instead of the last session. Layouts are listed in the menu and the command palette for switching at any time; the last session remains available as "Continue where I left off".

**Windows.** New window is one click (menu, Ctrl+N, or the + on the tab row with Shift) and opens with the start layout, placed as *Window geometry* says. Dragging a workspace tab, or a pane by its handle, and dropping it outside every window creates a new window holding it. Dragged onto another window it joins that window: on its tab row a tab moves there and a pane becomes a new workspace tab there; resting on one of that row's tabs spring-loads its workspace; and the dock targets appear on the pane under the cursor in whichever window that is, so a pane, or a tab holding exactly one pane, can be docked into a layout of the other window (see Workspace tabs). Every window has the full side panel and shares the operations queue, the preview follows focus across windows.

**Window geometry.** When Rick quits, the session holds for every window its position, its size, whether it was maximised and the monitor it was on; a maximised window's position and size are the ones it returns to when it is restored. On launch a window comes back exactly — monitor, position, size and maximised state — when its monitor is still connected and the window would be visible on it, which it is when the middle of its title row lies inside that monitor's working area, the monitor less the system's panels, dock and task bar. Otherwise — a first launch, the monitor gone, the position off-screen — the window opens centred in the working area of the primary monitor at the **default size**: its height is the smaller of 80 % of the working area's height and 1200 px, and its width is the smallest of 80 % of the working area's width, 1920 px and the height × 16/9. On an ordinary screen the 80 % decides; on an ultrawide one the 16:9 ratio keeps the window from spanning the screen; on a 4K screen the pixel cap does. A saved size that no longer fits its monitor's working area is clamped the same way — each side cut down to the default size's limit for that monitor — and the window is moved, where it must be, to lie inside the working area. A **second window** opens at the size of the window it was opened from, offset from it by a title row's height down and to the right, so that both can be grabbed; where that would take it past the working area's edge it starts again at the working area's top left corner. Sizes are in logical pixels. Session restore's tabs and panes come on top of all this. Where the platform gives an application neither its position nor a way to set it — a Wayland session — size and maximised state are saved and restored as above, and where the window is placed is the compositor's decision.

**Removed and unreachable locations.** One rule: a location that is gone for good sends its panes Home; a location that is only unreachable keeps the pane and retries.

- *Gone.* When the medium a pane is browsing is removed — pulled out, or ejected from the side panel — every pane showing a location on it, in every workspace of every window, goes to Home at once, and a toast says *<drive> was removed*, once per drive, naming the drive as its card does. *Eject* does this first and unmounts afterwards, so that no pane ever points at a drive that is gone and no listing keeps the drive busy. A location inside an archive or a disk image whose file is on the medium is on the medium too. The same holds when a cloud account or an SSH host is removed from the side panel while a pane is on it — *<account> was removed* — and when a provider is unmounted. Nothing about it is reported as an error.
- *Unreachable.* When a remote location stops answering — its provider reports a connection error, such as a timeout, a refused or reset connection or a name that does not resolve, and not a missing path or a refused permission — the pane stays where it is and shows, in place of the list, the File info card, centred (*File info card* under Preview): the head with the source's icon, *Connection lost to <account>*, naming the account or the host, and under it the provider's name; one row, *Error*, holding the provider's message; and an action row with **Retry** as its primary button. Rick retries by itself three times, 2, 5 and 15 seconds apart, and then waits for the button; a retry that succeeds shows the listing again where the pane was. Navigating away ends it. The pane goes Home only when the location is removed, as above.

**Opening files.** Enter or a double-click on a file opens it; nothing opens a viewer, because the preview pane is the only one. A folder navigates. An archive or a disk image (see *Disk images and Mount*) enters the file as a read-only location in the current pane through its provider; that is the default of the setting `archives.on_open` (`enter`), whose other value, `system`, hands the file to the OS default application instead. Every other file opens with the OS default application. Mod+Enter opens with the OS default application whatever the file and the setting, and *Open with…* stays in the context menu for all of them. Rick never writes to a file it shows; editing is the job of an external application via Open with.

*Remote files.* On a location with the `REMOTE` capability nothing is handed to the operating system: the file is not on the machine, and opening it with the system default is not attempted. Enter and a double-click on a remote file — an archive or a disk image included — start a **download** instead: the file is copied into the Downloads folder, the one Places resolves, or the home folder where the system has none, as a job in the operations drawer with its progress; a name that is already there is asked about with the paste-conflict dialogue; and nothing is opened when the job ends. Mod+Enter does the same, and *Open with* is not in a remote file's menu. A folder navigates as everywhere. **Download…**, in the Open group of the context menu of remote files and folders, does the same for the whole selection, folders included with everything beneath them, and asks for the target folder first, with the system's folder dialogue starting in Downloads. Both follow the location's `DOWNLOAD` capability (*Provider* under Core types): without it *Download…* is disabled with its tooltip and Enter on a file does nothing.

*Executables and scripts.* On the local file system a file with the execute bit is a program, and Enter and a double-click start it. A **binary** — a file with the execute bit whose first 4 KiB are not text, that is, hold a NUL byte — runs detached from Rick, with its folder as the working directory and without a question. An **executable script** — a text file with the execute bit — is a readable file as well, so Rick asks first, with the question dialogue: *Run script?*, the secondary line naming the file, and the buttons **Cancel**, **Edit** and **Run**, the primary one. *Run* starts the script in a console in its folder, so that its output is visible — the embedded console of *Open console*, or the system's terminal where `ext-action-terminal` is not loaded — and *Edit* opens it in the editor, below. A script without the execute bit is a text file like any other and opens with the OS default application. Mod+Enter and *Open with…* are unchanged. Windows has no execute bit: there every file is handed to the system as before, which runs a program and decides about a script by its association. This is what GNOME Files does, for the same reason.

*Open in editor.* **Open in editor**, in the Open group of the context menu of every local file and bound to F4, opens the selected files in the editor. Which editor is a setting, *Settings → Behaviour → Editor* (`editor` in `rick.toml`): empty, the default, is the system's default text editor, the application registered for plain text; anything else is a command — `code`, `rider`, with arguments if it needs them, split at spaces outside double quotes — that Rick starts with the files' paths appended. It is separate from *Open with…*, which stays the general picker, and it is not offered where the file has no path on the machine: on a remote location or inside an archive.

**Disk images and Mount.** A disk image is browsed like an archive: selecting it lists its contents in the preview pane, Enter enters it (above), and nothing is mounted for that — the provider reads the image file itself. The formats and the readers are in the Disk images table under Supported scope. *Mount* is an Action in the context menu of a disk-image file, and so also in the command palette, that hands the file to the operating system's own mount mechanism and nothing else: `Mount-DiskImage` on Windows (ISO, VHD, VHDX), `hdiutil attach` on macOS (DMG, ISO, IMG), `udisksctl loop-setup` on Linux (ISO and raw IMG), with a clear error when udisks is not installed. Rick ships no other mounting path (no qemu-nbd, no FUSE), and the action is hidden on a file the current OS cannot mount. The mounted image appears as a removable volume in the side panel's This Machine, and that row's *Eject* unmounts it; there is no separate Unmount action. The `platform` crate gains a `Mount` trait for this (which formats this OS mounts, mount a file), and the action lives in `ext-action-core`.
