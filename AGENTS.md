# Rick — agent instructions

You are implementing Rick (tagline: a god-like file manager), a cross-platform file manager in Rust. The
specification is SPEC.md in this repository. Read it before any task. It is
the source of truth: when code and spec disagree, the spec is right until it
is changed. Do not change SPEC.md yourself.

## How to work

- One task = one milestone or one issue. Do what the issue asks, nothing
  more. No speculative abstractions, no extra features, no settings the
  spec does not name.
- If the spec is ambiguous or contradictory for the task at hand, append a
  numbered question to QUESTIONS.md, make the smallest reasonable
  assumption, state it in the pull request description, and continue.
  Never resolve an ambiguity silently.
- Before opening a pull request, all of these pass locally:
  `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
  `cargo test --workspace`, `cargo deny check`, `cargo doc --no-deps`.
- Small commits, one concern each, conventional-commit messages
  (`feat(vfs): …`, `fix(ui): …`, `test(ops): …`). Each commit builds.
- The pull request description lists: what was done, what was assumed,
  which acceptance test proves it, what was deliberately left out.
- Branches: agent work lands on `dev`, and `main` only receives batches
  from `dev`. Every task branch opens its pull request against `dev`,
  never `main`. Serge merges finished pull requests into `dev` and tests
  them there by hand; when a batch is ready he opens one pull request from
  `dev` to `main`, which must pass the full matrix (CI tier 2) before it
  merges; after the merge `dev` is brought back level with `main`.

## Code rules (summary — SPEC.md "Engineering guidelines" and "Architecture rules" are authoritative)

- Rust 2024, stable toolchain pinned in rust-toolchain.toml.
- `unsafe` only in crate `platform`, every block with a `// SAFETY:` comment.
- `thiserror` in library crates, `anyhow` only in the `rick` binary.
  Never panic on user data or filesystem state.
- `tracing` for all logging; no `println!` outside tests.
- No `cfg(target_os)` outside `platform`.
- UI emits `Command`s, `app` handles them and publishes `Event`s. The UI
  never touches the model directly.
- Every long operation is a `Job` with a cancel token and progress.
- Entries are keyed by `EntryId`, never by path string.
- Crate dependency direction follows the layer order in SPEC.md and is
  enforced by cargo-deny. A dependency pointing upward is a bug.
- Every crate has a one-paragraph README.md: its responsibility and the
  crates it may depend on.
- Public items have doc comments. Each extension point has a worked
  example in its crate docs.

## Testing

- Unit tests next to the code. Integration tests in crate `tests`.
- The 200k-entry fixture is generated by `tests/fixture`, never committed.
- A bug fix adds a test that fails before the fix.
- Performance targets (SPEC.md Decisions table) are measured by the
  `bench` workflow (CI tier 3) on Linux, macOS and Windows: by hand, on
  release tags, and nightly on Linux x64; they never block a pull request.

## CI

Three tiers in `.github/workflows/` (issue 35). A new push to a branch
cancels its running check. A change to Markdown and `docs/` only builds
nothing, and the tier's gate job still reports success, so a docs-only
pull request is green in a minute; `BENCHMARKS.md` counts as code, a unit
test reads it.

- Tier 1, `ci.yml`: pull requests into `dev` and pushes to `dev`, Linux
  x64 only, a few minutes. `cargo fmt --check`, then side by side clippy
  with warnings denied and `cargo doc`, `cargo test --workspace` in debug,
  the bundle of the binary with every plugin and `--list-plugins` loading
  them, and `cargo deny`. Gate job `tier 1`.
- Tier 2, `full.yml`: the pull request from `dev` into `main`, nightly on
  `dev`, and by hand from the Actions tab. Tier 1's checks on Linux x64,
  Linux arm64, macOS arm64 and Windows x64, plus the integration tests on
  the 200k fixture (Linux x64) and the screenshots (Linux x64, macOS).
  Gate job `tier 2`, the check `main` requires.
- Tier 3, `bench.yml`: the acceptance benchmarks, measured with
  `RICK_BENCH_RECORD` and never blocking a pull request. By hand from the
  Actions tab and on `v*` tags on the three runners, with the logs as an
  artifact and the median and worst table in the job summary; nightly on
  `dev` on Linux x64, the summary committed to the `benchmark-history`
  branch so a regression can be traced to a day range.
- `release.yml` is unchanged: a `v*` tag builds the archives and publishes
  the release.
- The toolchain, cache, GStreamer, LibreOffice and pdfium setup is the
  composite action `.github/actions/setup`; the docs-only decision is
  `.github/scripts/docs-only.sh`.

## Platforms

- Linux, macOS and Windows are all first-class from 0.1. Pull requests
  into `dev` are checked on Linux x64 only (tier 1); the three platforms
  are required for dev → main (tier 2), so every batch builds and tests on
  all three before it reaches `main`.
